## Q1. Why is `MintsPage` fetching `getFindsForHeatmap`? Why `finds` instead of `sites`? Since the page can't filter/search anyway, wouldn't a map with plotted mints be enough?

**What it's actually used for.** `getFindsForHeatmap()` (full `finds` table) and `getCoinIssues()` (full `v_coin_issues_flat`) feed `computeMintStatsFromFinds()` ([lib/mint-stats.ts:108](lib/mint-stats.ts#L108)), which joins each find → `coin_issues_id` → `coinIssue.mint_zh` and aggregates, per mint: `findCount`, `coinCount` (summed quantity), `siteCount` (distinct `site_code`), and the set of inscriptions. In `app/mints/page.tsx` this output drives four things, not just the map:
- `mintPoints` — the small map preview
- `statsByMint` — the coin/site count shown on every mint's list card
- `typesByMint` — bilingual type tag chips per mint (from `coinIssues` directly)
- `issuesByMint` — the "number of issues" sort option (from `coinIssues` directly)

So it's not dead weight — the list below the map has real stat badges and a sort option that depend on it. If you only want "a map with plotted mints" as the demo, those card badges and the issue-count sort would need to go too.

**Why `finds` and not `sites`.** Coin *counts* and quantities are recorded at the find level (`quantity_total` etc. on `finds`), not on `sites` — a site can have many finds across many contexts, each tied to a different `coin_issues_id`. `sites` has no quantity or coin-type info at all, so you can't compute "how many coins from this mint" without going through `finds`. Using `finds` is structurally correct here; the problem is *how much* of `finds` and `coin_issues` gets pulled down to compute a few dozen numbers.

**The actual waste:** the entire `finds` table (every quantity/context/presence field, every row in the country) and the entire `coin_issues` catalog are shipped to the server just to produce ~40 mint-level aggregate rows. That's a textbook case for pushing the aggregation into Postgres instead of doing it in JS after a full fetch.

**Suggested fix:** add an aggregating view (see Q2) — e.g. `v_mint_stats` — that does the `finds` → `coin_issues` → `mints` join and `GROUP BY mint_zh` in SQL, returning one row per mint with `find_count`, `coin_count`, `site_count`, and inscriptions already aggregated. `MintsPage` would then `select * from v_mint_stats` (~40 rows) instead of pulling two full tables. `typesByMint`/`issuesByMint` would still need `coinIssues`, but that's a much smaller, single-purpose fetch than replicating the full catalog for stats too — worth checking whether a per-mint issue-count/type-tag aggregate could fold into the same view.

Note: `/visualizations/mint-town` (the full interactive viz) genuinely needs row-level `finds`/`coin_issues` for its live typology filtering, so this fix is specific to *unfiltered overview* consumers like `MintsPage`, not a wholesale replacement of `getFindsForHeatmap`.

## Q4. `app/coin-types/[slug]/page.tsx` also calls `getFindsForHeatmap()` — is that strictly necessary? Can there be a modified function that pulls only the already-filtered finds instead of processing everything after fetching?

**What `finds` is used for here** ([app/coin-types/\[slug\]/page.tsx:71-129](app/coin-types/%5Bslug%5D/page.tsx#L71-L129)), for a page that renders exactly **one coin type node**:
1. `computeCoinTypeCounts(node.matchedHierarchyIds, finds, hierarchyIdByIssueId)` ([lib/coin-type-catalog.ts:286](lib/coin-type-catalog.ts#L286)) — walks every find, resolves its `coin_issues_id` → hierarchy id, and counts it only if that hierarchy id is in `node.matchedHierarchyIds` (this node + its descendants). Produces one `{coinCount, findCount, siteCount}` for the "Coins & sites" row.
2. `matchedSiteCodes` (page.tsx:124-129) — same filter pattern, collecting `site_code` from finds that match, to narrow the full `sites` list down to `relatedSites` for the "Related Finds" table.

Both uses only ever care about finds whose `coin_issues_id` belongs to a small, already-known set (`matchedIssueIds`, derived from `coinIssues` — a catalog-sized fetch, not a per-find one — a few lines above at page.tsx:120-123). Every other find in the database (every other coin type, every other mint) is fetched and then thrown away by the `.filter()`/`.forEach()` calls. **This is not necessary** — it's filtering client-side something that could be filtered in the query itself.

RESPONSE: GET RID OF IT.

**Yes, this codebase already has the exact pattern needed.** `getFindsForSiteCodes(siteCodes)` ([lib/queries.ts:1028](lib/queries.ts#L1028)) already does "fetch only the finds matching a known id list" for site codes. The same shape, applied to issue ids instead, is a small addition:

```ts
export async function getFindsByIssueIds(issueIds: string[]): Promise<HeatmapFind[]> {
  if (issueIds.length === 0) return []
  return fetchAllPages<HeatmapFind>((from, to) =>
    supabase
      .from('finds')
      .select('coin_issues_id, context_code, quantity_total, quantity_min, quantity_estimated, presence, contexts!inner(site_code)')
      .in('coin_issues_id', issueIds)
      .order('find_code')
      .range(from, to)
  )
}
```

Then in the page: compute `matchedIssueIds` from `coinIssues` first (already happening at line 120-123, just needs to move above the `Promise.all`), and call `getFindsByIssueIds([...matchedIssueIds])` instead of `getFindsForHeatmap()`. For any coin type that isn't one of the handful of very common ones, this drops the finds fetch from "every find in the country" to "the dozens/hundreds of finds of this one type" — and this page is hit once per coin-type slug, so the saving multiplies across every type detail view, not just once.

One caveat: `matchedIssueIds` could be large for a broad level1/level2 node (e.g. "钱币" itself) where `.in(...)` with thousands of ids gets unwieldy in a single PostgREST call — worth chunking (same `CHUNK`-based pattern `getFindsForSiteCodes` already uses) or falling back to a hierarchy-id join (`coin_issues!inner(coin_type_hierarchy_id)` with `.in('coin_issues.coin_type_hierarchy_id', matchedHierarchyIds)`) if so. Either way, still far less than the full table.

1. **Move the auth check to the client (small, scoped, fixes just these 3 routes).** Since the only things gated on `authorized` are small UI affordances — the "+ Add mint" button, edit comboboxes, dev-only "Database Record" panels — none of that needs to be resolved during the server render. **Recommendation:** do #1 now (small, low-risk, fixes exactly this bug on exactly these 3 routes) using the existing `authorized` boolean pattern already threaded through every one of these pages. ## Q6. How would I make `/sites/[site_code]`, `/mints/[mint_code]`, `/coin-types/[slug]` only ever fetch one row (or the minimum needed)? Why is it `[slug]` and not `[type_code]`? Since coin-types aggregates across many rows, how do I minimize that fetch?

### Why `[slug]`, and why not the same pattern as the other two

`[site_code]` and `[mint_code]` are Next.js dynamic route segments named after a real, stable database column — `sites.site_code` and `mints.mint_code` — so the page can do a direct `.eq('site_code', siteCode)` lookup. One code, one row, no ambiguity.

`coin-types` can't use the same trick, because a coin type isn't one flat table — it's a 5-level tree (`coin_type_hierarchy.level1`..`level5`), and a page can exist for a node at *any* level (a broad category like "刀币" Knife Money, all the way down to one specific variant). There's no single column that names "this node at whatever level it happens to be" — `coin_type_code` only identifies leaf-level rows. So `buildCoinTypeNodes()` computes a **slug per node at request time**, via `slugify()` over the node's label + `uniqueSlug()` for collision handling ([lib/coin-type-catalog.ts:66-73](lib/coin-type-catalog.ts#L66-L73), full node-building starts ~line 90). It's a derived identifier, not a stored one — `[slug]` names that it's a computed router param, not a raw column, the same way you'd see `[slug]` on a blog post whose URL is derived from its title rather than a numeric id.

**Consequence for "one row":** for `/sites/[site_code]` and `/mints/[mint_code]`, "one row" is the literal right target — one site, one mint. For `/coin-types/[slug]`, it depends on the node's level: a leaf node (level5) really does correspond to ~one `coin_type_hierarchy` row, but a level1/level2 node is *by design* a grouping bucket over many rows (`node.matchedHierarchyIds` is an array for exactly this reason — see [lib/coin-type-catalog.ts:39](lib/coin-type-catalog.ts#L39)). So the right framing there isn't "fetch one row," it's "fetch only the rows under this node's subtree, however many that is" — i.e. scope every related query to `matchedHierarchyIds`/the issue ids derived from it, instead of fetching the whole database and filtering client-side (this is exactly Q4's finding).

This is real-world confirmation that the `getFindsByIssueIds`-style pattern proposed for `/coin-types/[slug]` in Q4 is not hypothetical — it's already load-bearing elsewhere in this codebase, just not factored out into a shared, reusable function.
- The actual waste is earlier, in `resolveMintPage()` ([page.tsx:40-44](app/mints/%5Bmint_code%5D/page.tsx#L40-L44)): it calls `getMints()` (full `mints` table) + `getImages()` (full `images` table) just to find **one** mint by `mint_code` via a JS `.find()` inside `getMintDirectoryEntryBySlug`. `mints` is presumably small (a bounded historical set of mint towns), but there's no reason to fetch it in full when `getSite` right next door already shows the correct pattern. Fix: add `getMintByCode(mintCode)` mirroring `getSite` exactly:
  ```ts
  export const getMintByCode = cache(async function getMintByCode(mintCode: string): Promise<MintRow | null> {
    const { data, error } = await supabase
      .from('mints')
      .select('id, name_zh, name_en, precision_level, latitude, longitude, description_zh, description_en, citation, modern_location_zh, modern_location_en, location_note, state_id, states(state_zh, state_en), image_ids, sources_unlinked, mint_code, alternative_names')
      .eq('mint_code', mintCode)
      .maybeSingle()
    if (error) throw error
    return data
  })
  ```
  (Images would still need a `.overlaps()`/`.in()` lookup against `mint.image_ids` rather than a full `getImages()` scan — worth checking `getImages()`'s shape before assuming this is a drop-in swap.)
- `getCoinIssues()` + `getCoinTypeHierarchy()` (full, [page.tsx:73-74](app/mints/%5Bmint_code%5D/page.tsx#L73-L74)) are fetched just to resolve `distribution.typeLabels` (already a short, mint-scoped list from `getMintFindspotsData`) to their catalog slugs. Both tables are small (~487 rows) so this isn't a major egress line item, but it's still more than needed — same category as the `/sites/[site_code]` leftovers above, low priority relative to the caching-bug fix.

**`/coin-types/[slug]`** — the one with a real, large-table problem (covered in depth in Q4):
- `getCoinTypeHierarchy()` (full, small ~487 rows) — legitimately needs to stay full-table here: building the tree and resolving parent/child/slug relationships inherently requires the whole hierarchy, not just this node's subtree, and it's cheap. Don't bother scoping this one.
- `getCoinIssues()` (full, ~487 rows) — same as above, technically a full scan but on a small table. Could in principle be scoped to `.in('coin_type_hierarchy_id', matchedHierarchyIds)` once `matchedHierarchyIds` is known (which only requires the hierarchy, not the issues) — but given the table's actual size, this is a nice-to-have, not where the egress is.
- `getFindsForHeatmap()` (full, `finds` — the actually large table) — **this is the real problem**, covered in Q4: replace with a scoped `getFindsByIssueIds(matchedIssueIds)`, computed from `matchedIssueIds` (already derived from `coinIssues` a few lines above the current fetch). This single change is the highest-value fix on this page.
- `getFindSpotsMapSites()` (full, [page.tsx:75](app/coin-types/%5Bslug%5D/page.tsx#L75)) — fetches every mapped site in the database (`v_coin_map_sites` + precision-supplement queries, [lib/queries.ts:606-609](lib/queries.ts#L606-L609)) just to filter down to `relatedSites`, the handful of sites with a find of this one type ([page.tsx:130-132](app/coin-types/%5Bslug%5D/page.tsx#L130-L132)). `sites` is a modest table (~561 rows) so this isn't `finds`-scale, but it's still a full scan plus its own internal multi-query fanout (supplement queries + `fillMissingMapSiteTypes`) for a page that only needs a handful of rows. Once `matchedSiteCodes` is known (currently computed *after* the fetch, from the `finds` loop — reorder so it's known first), a scoped `getMapSitesByCodes(siteCodes)` with `.in('site_code', siteCodes)` on `v_coin_map_sites` would replace it, skipping the supplement/fill-missing-types machinery entirely for this page (that machinery exists to patch up sites across the *whole* map, which isn't relevant when you already know the exact site codes you want).

### Summary — where "minimize the fetch" actually pays off here

Ranked by table size × how full the current scan is:
1. **`getFindsForHeatmap()` on `/coin-types/[slug]`** (Q4's fix) — large table, full scan, purely wasted. Highest value.
2. **`getFindSpotsMapSites()` on `/coin-types/[slug]`** — modest table, full scan plus multi-query fanout, mostly wasted. Worth doing once #1 is done.
3. ✅ **`resolveMintPage()`'s `getMints()`+`getImages()` on `/mints/[mint_code]`** — small table(s), full scan for a single-row lookup; cheap in bytes but easy, correct fix (mirrors `getSite` exactly) — do it for consistency even if the byte savings are modest. **Applied:** `getMintByCode(mintCode)` ([lib/queries.ts](lib/queries.ts)) + `getImagesByIds(ids)` scoped to the mint's own `image_ids`; `resolveMintPage` now calls both instead of `getMints()`+`getImages()`.
4. **`getCoinIssues()`/`getCoinTypeHierarchy()` full scans** anywhere they appear — technically full scans, but on ~487-row tables. Low priority; not where the 1.7GB/day is coming from.
5. **The `isAuthorized()`-forces-dynamic-render bug**, shared by all three of these detail-page families — this isn't a row-scoping issue at all, but it multiplies *every* fetch above by "once per visit" instead of "once per 24h," so it's arguably more impactful than any individual query-scoping fix in this section. Worth fixing alongside, not instead of, the scoping work above.
