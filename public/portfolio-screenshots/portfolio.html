Overview

A research tool, not just a dataset

The database catalogues archaeological discoveries of pre-Qin to early Han coinage across China. Every record links a find site to its geographic location, archaeological context, coin typology, and bibliographic sources — queryable directly from Supabase, with a handful of stable reference datasets (mint-town dossiers, typology hierarchy, specimen photography) kept local for anything that rarely changes.

It's built for three kinds of use: browsing curated catalogs (Mints, Coin Types), free-form searching and filtering (Search, Museum Collections), and spatial analysis (the Map Visualizations views — points, density heatmaps, and side-by-side comparison). There's no API layer in between: React Server Components query Supabase directly at render time.

Live pieces at a glance
  • Full-text + faceted search across every find site
  • Three interactive map visualization modes shared across three datasets
  • A bilingual (EN/ZH) UI with zero hardcoded copy — every string is a dictionary lookup, switched with no page reload
  • In-place admin editing, gated by Supabase Auth + Postgres row-level security
  • ANS museum specimen reconciliation, searchable by accession number
Search

Full-text and faceted search

Every find site is searchable by name, province, coin type, inscription, or site code, with facet filters for region, period, site type, coin type, state, mint, and quantity — plus a results map that clusters by count. Every facet computes live counts from the current query (e.g. "河南 (289)"), not a static list.

  • Sortable by a blended relevance score (the default), name, quantity, region, find count, coin-type diversity, mint diversity, or state diversity
  • Location-precision filter (site / county / city / all) with a click-to-explain badge on "All," since it deliberately surfaces real gaps in geolocation precision rather than hiding them
  • Each coin-type label carries a color swatch from the same palette the per-site pie chart slices use, so a type reads as the same color everywhere it shows up on the page
Site Records

One page per archaeological site

Location, a "Coin Mint Origins" map connecting the site to every mint it received coins from (dashed lines, auto-jittered pins where two mints share a coordinate), classification, and a tabbed breakdown of excavation contexts, individual finds, and citations — all in one record, linked to from Search, mint pages, and coin-type pages alike.

Mints

Every documented mint town

A searchable, sortable directory of mint towns — merging live database rows with hand-transcribed dossiers (location, description, images, citations) wherever the database doesn't carry a field yet, and clearly flagging which is which.

  • Sort by number of finds, number of coins, number of catalogued issues, or completeness of the record
  • Static, English-only reference data is visually distinguished (dashed border) from live, bilingual database data — never silently mixed
Mint Detail

Location, coin output, and primary sources

Each mint's own page: coordinates on a detail map, an issued-coin distribution map filterable by coin type, an image gallery for historical city plans, and full bilingual citations back to the original excavation reports. A "geolocation is provisional" warning surfaces automatically wherever the dossier flags an uncertain placement.

Coin Types

The full typology, browsable two ways at once

Every documented coin type as a searchable card grid and a full expandable hierarchy tree (钱币/Coin and 钱范/Mould branches), each card showing obverse/reverse photography where available, sortable by hierarchy level, find count, coin count, or catalogued issues.

Coin Type Detail

One typology node, fully cross-referenced

Obverse/reverse images, parent types, every issuing state and mint, every attested inscription, a collapsible coin-issue catalogue, related find sites, and this node's place in the overall hierarchy tree. Photography is matched to a type at request time by filename-prefix lookup — types without a photographed specimen fall back to a plain placeholder rather than a broken image.

Map Visualizations

Three ways to see the same geography /visualizations/find-site /visualizations/mint-town

Find Site, Mint Town, and Museum Collections all share one full-bleed map engine — MapVisCanvas plus three sibling orchestrator components — with Points / Density / Compare display modes, each filterable by Coin Type or Mint. Click-to-reveal explanations on every non-obvious control (View by, Filter by, Display) let the interface teach itself. Landing on /visualizations itself drops you into a random one of the two tabs.

The unfiltered national view keeps Points mode readable by clustering markers into count bubbles; picking a Coin Type or Mint filter unclusters them into individual ratio-colored dots. A layer switcher swaps the default CyclOSM base for plain OpenStreetMap, Esri satellite imagery, a hillshaded terrain basemap, or 高德/AutoNavi tiles for reading present-day Chinese place names.

Case study — fixing the route overlay. The orange trade-route network visible on several maps above (digitized from a Tang-dynasty route shapefile) is a live example of a bug fixed in this same codebase: the route lines and their named-node markers were digitized independently, so nodes sat up to ~2 km off their line at high zoom, and clicking a route triggered the browser's default focus outline as a giant rectangle around the line's full bounding box. The fix projects each node onto its nearest route segment (scripts/route-node-snap.mjs) and suppresses the stray focus ring in app/maps.css — 246 of 251 nodes moved onto their line, verified with a side-by-side before/after render.

Reconciled specimens, same map engine /museum-collections

Data model

Schema & data sources

The core find-provenance chain, plus how sources and citations tie back to every record.

The provenance chain is sites → contexts (an archaeological findspot within a site — a tomb, hoard pit, stratum) → finds (a reported coin group from one context, per one source) → coin_items (individually catalogued specimens, defined but not yet surfaced by the app). Every quantity shown in the UI comes from the finds-level quantity fields, not from counting itemized rows.

A dedicated ans_data table holds reconciled American Numismatic Society specimens (mint/state/hierarchy/inscription already resolved per row), feeding Museum Collections independently of the database's own find records. Supabase's REST API caps a single response at 1000 rows — several tables here exceed that, so every multi-row query pages through a shared fetchAllPages() helper rather than silently truncating.

Request → page, in one line Browser hits a Server Component → it awaits lib/queries.ts functions that hit Supabase over HTTPS → results pass down as plain props into a 'use client' component → that component owns all interactive state and the Leaflet map instance. No further round-trip happens until the user navigates.

How sources & citations work

A source_links join table connects each sources row to whichever site, context, find, or mint it documents. Nothing is a free-text citation string embedded in a record — every citation is a real row in that join table, so removing or re-attaching a source never requires editing the record it's cited on.

The dedicated Sources browser lists all 1,161 catalogued sources and 9,716 linked citations, searchable by code, author, title, publication, or citation text, with an inline "+ Add source" form. Every place a citation shows up — a site's own Sources & Citations tab (seen above), a mint page, or the Sources browser itself — reads from this same table and offers the same quick-remove control per citation.

Static + live, merged per field. Mint town profiles merge a live Supabase row with a static, hand-transcribed dossier — the database wins wherever it has a value, the dossier fills gaps — rather than forcing a full migration before every field can be shown.

Interactive · security-gated

Admin editing & deletion protections /sources

The app is read-only for anonymous visitors, but every record — sites, contexts, mints, sources, and the citations linking them — has an in-place edit form for authorized collaborators, no separate admin dashboard required. Editing is gated twice: once at the UI level (hidden entirely for anonymous visitors in production) and again, non-negotiably, at the database level via Postgres row-level security policies keyed to a shared is_admin() function — so the real enforcement boundary is the database, not the UI.

Deletion protection: typed confirm, no bulk table wipe Every delete action anywhere in the admin UI — a context, a find, a source, a single citation — routes through one shared confirm control: clicking Delete opens an inline popover whose Confirm button stays disabled until you type the word delete into its field. There's no "wipe this whole table" action anywhere in the app; the closest equivalent is the Sources browser's per-citation remove next to each "cited by" row above — the same typed-confirm popover, just scoped to one link at a time rather than a bulk operation.
In local development, authorization checks always pass (there's nothing to sign into yet) — every edit-form screenshot on this page was taken from that dev-mode view, which is exactly why it was safe to capture without a real session.
Cross-cutting

Mobile

Below the lg breakpoint, the desktop horizontal nav collapses into a hamburger menu; full-bleed map pages (the two visualizations tabs and Museum Collections) hide the site footer entirely so the map gets the whole viewport, and every floating filter panel that's always-open on desktop becomes a collapsible drawer instead of just shrinking in place. Shown here at Mobile‑L width (~390–425px) rather than stretched to the desktop screenshots' full size, so the frames actually read as a phone.

Internationalization, mechanically. Every piece of UI copy is a lookup against a flat { key: { en, zh } } dictionary — nothing is a hardcoded string in a component. There's no locale-based routing; a client-side context defaults to English for SSR-safety, then corrects to whatever's saved in localStorage right after mount — which is what makes the 中文 toggle instant on every page, not just Home.
Worth knowing

Engineering notes

A few decisions that don't show up in a screenshot but shape how the whole thing holds together.

  • No API layer, no Server Actions for reads. Server Components call lib/queries.ts directly; the anon Supabase key is safe to expose because every table it reads is public catalogue data and reads never write.
  • Pagination that doesn't silently truncate. Supabase's PostgREST caps responses at 1000 rows; fetchAllPages() pages through .range() until a short page comes back, since sites, finds, and contexts all exceed that cap.
  • Repeated joins pushed into SQL views. v_coin_issues_flat and v_source_link_targets pre-join coin issues and source-link targets in Postgres — with major/minor type already derived — so the app reads a flat row instead of embedding + reshaping the join client-side on every call.
  • One canvas, three call sites. MapVisCanvas and its three sibling orchestrators mean "how a marker gets drawn, sized, and reconciled across re-renders" is written exactly once, even though it backs three visually distinct pages.
  • Hand-rolled data visualization. No charting library anywhere — the site-detail pie charts are raw SVG, and every "chart" on the site is actually the Leaflet map itself, styled through one shared color-ramp module.
  • Security lives in Postgres, not just the UI. Admin write access is enforced by row-level-security policies calling a shared is_admin() function — the same check the UI uses to decide whether to render an Edit button, so a bypassed UI still can't write.
  • Type system split deliberately in two. DB-shaped types mirror what Supabase returns; rendering-shaped types are defined next to the component that consumes them and imported back into the functions that produce them, so "the shape a map needs" is defined exactly once, at the map.
